Hotfix for a price-inflation regression introduced in v0.1.75: on Modul-1 sites that started receiving a §14a Modul-3 preview payload from the backend, the all-in price sensor was adding a grid-fee that the vendor does not actually bill. v0.1.77 trusts the SDK's own all-in dict again — the preview is kept, but only on its own sensor.

## Fixed

**`sensor.<sys>_current_electricity_price` reads `prices_with_grid_costs_and_vat` directly again.** v0.1.75 composed the all-in price per-slot from `spot + fixed + enwg14a_grid_fee`, treating a non-empty `MarketPrices.enwg14a_grid_fee` dict as "Modul 3 live." Backend reality on Modul-1 sites: the dict is populated with a flat preview value (e.g. 0.0717 €/kWh across all slots) while `grid_cost_dynamic_markup` stays at 0 and `prices_with_grid_costs_and_vat` likewise excludes the preview. The vendor's billed number is the SDK dict; our composition was adding the preview on top. On an affected site this made the sensor read `~0.59 €/kWh` instead of the billed `~0.51 €/kWh` (a `+0.085 €/kWh = enwg14a_grid_fee × 1.19` delta). The sensor now trusts the SDK dict verbatim and keeps the composition only as a defensive fallback for when the dict is empty.

**`grid_cost_components.dynamic_markup` on `sensor.<sys>_current_electricity_price` reports the billed scalar.** The breakdown attribute mirrored the per-slot preview in v0.1.75; it now surfaces `grid_cost_dynamic_markup` again (the Scalar the vendor bills). `grid_costs` reconciles accordingly.

## Compatibility

`sensor.<sys>_enwg14a_grid_fee_current` is unchanged — the Modul-3 preview series remains visible on its own sensor and 30 h forecast attribute. When the backend promotes Modul 3 from preview to billed, `prices_with_grid_costs_and_vat` will carry the slot-variable number natively and the sensor already surfaces that correctly without further code changes. 466 tests green, `mypy --strict` clean, `ruff` clean, Python 3.14 + HA 2026.10.2.
