A new live §14a-Modul-3 grid-fee sensor plus a vendor-side rate-limit mitigation. Behaviour-only on existing entities; one new entity added.

## Added

**`sensor.<sys>_enwg14a_grid_fee_current`** — live §14a-EnWG-Netzentgelt per kWh for the active 15-minute slot, parented on the meter sub-device. State is the net value in `€/kWh`; the VAT-inclusive counterpart lives on the `price_with_vat` attribute so automations can key off either number.

Populated for **§14a Modul 3** sites (variable Netzentgelte HT/NT), where the time-of-day rate is the point of the module. Stays unavailable on **Modul 1** sites (flat annual rebate — the annual value already lives on `module1_grid_fee_reduction_annual`) because Modul 1 has no per-slot component. Non-§14a sites see the same unavailable state, so automations degrade cleanly.

## Changed

**Price coordinator skips the tomorrow-fetch before 12:00 UTC.** The 1KOMMA5° `/charts/market-prices` endpoint is BigQuery-backed with a shared 100-second `JobService.query` quota per account. EPEX publishes day-ahead prices at 12:00 UTC (13:00 CET winter / 14:00 CEST summer), so every tomorrow fetch before noon UTC was a guaranteed empty call that only chipped at the quota and raised the risk of 403 "Exceeded rate limits" bursts when the hourly refresh lined up with Flutter-app traffic. Today's fetch stays unconditional (feeds the gradually filling `gridConsumption` / `gridFeedIn` series). Impact: ~12 saved requests per day per instance; burst-at-the-hour exposure halved in the quota-sensitive window.

**SDK pin raised to `onekommafive>=1.2.2,<2`** across `pyproject.toml` and `manifest.json`. v1.2.1 adds the per-slot §14a-Modul-3 grid-fee data (`MarketPrices.enwg14a_grid_fee`) consumed by the new sensor above. v1.2.2 adds a transparent client-side retry-with-backoff for the vendor's 403 "Exceeded rate limits" / 429 responses — so the coordinator-side 12-UTC gate combines with SDK-level resilience against the shared BigQuery quota.

**Documentation sharpened** for Modul-1 vs Modul-3 semantics across `docs/features/enwg14a.md`, `docs/faq.md`, and the sensor docstring. Added a FAQ entry explaining why `enwg14a_grid_fee_current` stays unavailable on Modul-1 sites (semantically correct, not a bug).

## Compatibility

Behaviour-only on existing entities, one new entity. Automations that key on the new sensor must handle `unavailable` (that is the normal state on all non-Modul-3 sites). `mypy --strict` clean, ruff clean, 412 tests green on Python 3.14 + HA 2026.10.2.
