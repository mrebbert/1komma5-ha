Adds a §14a-Modul-1 meter sensor plus the usual internal hygiene: SDK pin bump, Ruff-line-length convergence, and multi-EV dashboard documentation. Existing automations continue to work with the same schema.

## Added

**`sensor.<sys>_meter_module1_grid_fee_reduction_annual`** — annual net §14a-EnWG Modul 1 grid-fee reduction (EUR/year), parented on the meter sub-device. Reads `HeartbeatPriceWindow.module1_savings_per_year_eur` from the SDK's `get_heartbeat_prices` endpoint. The sensor stays `unavailable` when the account carries no provisioning date — sites without an iMSys plus a controllable consumption device (wallbox, heat pump, PV battery) see no sensor value, which is semantically correct and matches the regulatory precondition for §14a.

Attributes expose:

- `provisioning_date` — ISO date the Modul-1 bundle went live on the account.
- `active_days` — days the bundle counted as active in the one-year window (365 at steady state).
- `gross_estimate_eur_assumption` — `value × 1.19`, flagged in the attribute name as an assumption. Confirmed on the first observed account (121 € net API vs 144 € published gross for the tariff area); the SDK notes a second data point from a different grid area is still pending.
- `basis` — "§14a EnWG Modul 1 (BNetzA BK6-22-300); working hypothesis, net figure".

The sensor sits under the diagnostic entity category to keep it out of the main device card. `electricity_cost`, `stable_electricity_price` and `feed_in_revenue` are deliberately **not** modified: Modul 1 is an annual grid-fee rebate, not a per-kWh discount, so linearising it onto the spot-price sensors would be misleading. The reduction stands next to the usage sensors, not inside them.

**New `heartbeat_prices` coordinator** on a 1 h cadence, backing the sensor above. The call is non-fatal at first refresh (same policy as the price and energy coordinators), so a rate-limited initial fetch just leaves the sensor unavailable until the next tick. `onekommafive.refresh_now` accepts `coordinator: heartbeat_prices`, and the diagnostic-timestamp set gains `sensor.<sys>_diag_heartbeat_prices_update`.

**Four additional AI-optimization decision binaries.** The optimization endpoint carries seven decision strings; v0.1.65 exposed two of them as dedicated binary sensors (`BATTERY_CHARGE_FROM_GRID`, `HEATPUMP_RECOMMEND_ON`). This release adds the remaining four actionable ones:

- `binary_sensor.<sys>_optimization_battery_grid_discharge` — ON while `BATTERY_DISCHARGE_TO_GRID` is the active decision (the AI sells battery energy at the spot market). Parented on the inverter sub-device.
- `binary_sensor.<sys>_optimization_battery_no_charge` — ON while the AI actively suppresses battery charging.
- `binary_sensor.<sys>_optimization_battery_no_discharge` — ON while the AI reserves the battery for a later slot. Useful for the "why am I buying from the grid despite SoC above 20 %" question.
- `binary_sensor.<sys>_optimization_ev_grid_charge` — ON while `EV_CHARGE_FROM_GRID` is active (the AI schedules EV charging from the grid). Parented on the wallbox sub-device.

`HEATPUMP_AUTO` stays out as the no-op default. Automations can now trigger directly on the matching decision instead of pattern-matching the text state of `sensor.<sys>_optimization_last_decision`. All four follow the same `OptimizationDecisionSpec` shape as the pre-existing two binaries, so icons, translations and the shared `is_on` implementation stay consistent.

## Changed

**SDK pin bumped to `onekommafive>=1.1.3,<2`** (from `>=1.0.3,<2`). Home Assistant installs the new SDK on first reload after the update; no manual step required. The v1.1 line continues the async aiohttp surface with `py.typed`, so the integration keeps its `mypy --strict` clean stance. The bump also captures an upstream API alignment: `System.get_optimizations(start, end)` now sends `view=historic` (v1.1.1) in anticipation of the 1KOMMA5° endpoint enforcing that parameter; without it, once enforcement lands, the response would collapse to an empty `events` list without a warning. As of 2026-09-28 the endpoint still returns identical payloads with and without the parameter, so no existing install currently sees a regression; the bump is a proactive guardrail. v1.1.1 additionally introduces `System.get_live_optimizations()` for the currently running optimisation slot; the integration itself does not consume it yet. v1.1.2 exposes four new `module1_*` fields on `HeartbeatPriceWindow` (provisioning date, active days, per-year / total net savings), which the Modul-1 sensor above now consumes; v1.1.3 documents the §14a-EnWG interpretation that frames the sensor.

**Ruff line-length lowered from 100 to 88.** The Home Assistant core Ruff config uses 88; aligning removes the last non-default choice in the repo's style stack. `ruff format` reformatted 54 files (193 lines rewrapped automatically) plus 41 manual cleanups (docstring trims, inline-comment relocations, a couple of factored-out f-strings and long test-fixture lines). No entity or code-path behaviour changed.

**`.git-blame-ignore-revs` added.** The two reformat commits (config switch + manual cleanups) are recorded so `git blame` continues to point at the substantive authors of each line. GitHub honours the file automatically; contributors enable it locally once with `git config blame.ignoreRevsFile .git-blame-ignore-revs`. `CONTRIBUTING.md` gains a short "Ignoring reformat commits in `git blame`" section.

**Example dashboards restructured for multi-EV assignments.** `dashboard/dashboard.yaml` and `dashboard/dashboard-showcase.yaml` now stack the Fahrzeug view as *Wallbox → Fahrzeug* → *Lademodus* → *Smart-Charge Einstellungen*, with per-EV conditional blocks that follow the currently-assigned vehicle. Placeholders switch from `CAR_IDENTIFIER` to `EV_N_PREFIX` / `EV_N_SLUG`, one duplication per EV. The Fahrzeug screenshot in `dashboard/README.md` and the placeholder table there are updated accordingly. Also fixes a latent Smart-Charge-visibility bug (the previous condition compared the read-only `sensor.…_lademodus` uppercase state against a lowercase value; the new blocks compare against the `select.…_lademodus` state).
