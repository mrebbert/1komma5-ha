v0.1.63: control the wallbox → vehicle assignment from Home Assistant (feature request #24), plus the optimization-slot correction that was armed as v0.1.62 and folded into this release. Backed by SDK `0.5.0`.

## Added

**`select.<sys>_<wallbox>_assigned_vehicle`** — one select entity per physical wallbox, parented on the wallbox sub-device. The options are the site's vehicle profiles (e.g. `bmw_i3`, `tesla_model_y`); the state reflects `Wallbox.assigned_ev_id`. Selecting an option calls the 1KOMMA5° API's assignment endpoint. The 1KOMMA5° model is 1:1 exclusive: setting the assignment on one vehicle automatically releases whichever vehicle was previously bound to the same wallbox — a single call does both sides. Sites with a single vehicle see the entity but have nothing to switch (no UI breakage, just an inert control).

**Service `onekommafive.assign_ev_to_wallbox`** — id-addressed counterpart to the select for automations that carry the vehicle and wallbox as data rather than as an entity slug. Schema: `wallbox_id`, `ev_id` (both required). Returns `{success, previous_ev_id}` so automations can log the swap. Rejects unknown ids with a clear `HomeAssistantError`.

**Blueprint `vehicle_at_wallbox.yaml`** — one automation per vehicle. Trigger = the vehicle's plug-in binary sensor (from a car integration or a smart-plug helper) flips to `on`; action = the wallbox's assignment select is set to that vehicle. Turns "car plugs in" into "1KOMMA5° binds the right profile" without hand-crafting the automation.

**EV view in the example dashboards gains a *Wallbox → Fahrzeug* card.** `dashboard/dashboard.yaml` and `dashboard/dashboard-showcase.yaml` reference the new select using the same placeholder convention as the rest of the file (`SYSTEM_NAME` for single-wallbox setups; per-wallbox slugs for multi-wallbox sites).

**Wallbox inventory in system-status coordinator.** The 5-minute-cadence system-status coordinator now also carries the wallbox list with live `assigned_ev_id`. Needed to drive the assignment select without a dedicated coordinator; not surfaced as a user-facing entity on its own.

## Fixed

**`sensor.<sys>_optimization_event_count` counts 15-minute slots, not event objects.** The `/heartbeat-ai/optimizations` endpoint aggregates consecutive same-decision slots within a one-hour bucket into a single event object. Counting objects silently under-reported the day's decision volume by up to a factor of four. The sensor now sums `OptimizationEvent.slot_count` across events. Expect a one-time step up on the first refresh after the update: the new value is correct; the previous one was too low.

**`binary_sensor.<sys>_optimization_battery_grid_charge` and `binary_sensor.<sys>_heatpump_recommendation` stay on for the full slot span.** These sensors previously flipped back to `off` at the 15-minute mark of an aggregated hour-long decision, because the active-window check compared against `to_time` (first slot only). Now they use `end_time` (aggregated span end), so a 60-minute `BATTERY_CHARGE_FROM_GRID` decision reads as on for the full hour. Falls back to `to_time` on older SDK payloads.

## Changed

**Attribute `to` on `sensor.<sys>_optimization_last_decision` reflects the aggregated span end.** Was: the end of the first covered slot. Now: the end of the last covered slot. The `decisions[]` entries under `sensor.<sys>_optimization_event_count` get the same treatment. Both surfaces gain a new `slot_count` attribute (integer, `1` for a single-slot decision, up to `4` for a hour-long aggregation).

**Bus event `onekommafive_optimization_decision` gains `end` and `slot_count`.** The existing `to` field stays untouched (still equal to the first-slot end) for automation-payload compatibility. `end` (aggregated span end) and `slot_count` (integer) join as first-class fields for automations that want the corrected values.

**SDK pin `>=0.5.0,<0.6` (from `>=0.4.0,<0.5`).** Upstream `0.4.1` is contributor-tooling only (uv lockfile in the repo, Dependabot switched to the uv ecosystem, second CI job that runs `uv sync --frozen && uv run pytest`). `0.4.2` documents the aggregated optimization-events semantics and adds the `slot_count` / `end_time` accessors that back the optimization fixes above. `0.5.0` adds `EVCharger.assign_charger(charger_id)` — the write path that backs the assignment surface.

## Automation pattern

```yaml
automation:
  trigger:
    platform: state
    entity_id: binary_sensor.model_y_charger_connected
    to: "on"
  action:
    service: select.select_option
    target:
      entity_id: select.wallbox_assigned_vehicle
    data:
      option: tesla_model_y
```

Home Assistant detects which vehicle is physically connected (via another integration); the assignment select tells 1KOMMA5° which vehicle profile — and therefore which charging mode and target SoC — applies to the ongoing session.
