v0.1.52 — notifications event bridge, plus two smaller surfaces off the new SDK endpoints. No breaking changes, no migration.

## Added

**Bus event `onekommafive_notification`.** Fires once for each newly-observed cloud notification (energy market thresholds, system health alerts, dynamic-pulse events, …), so you can drive Home Assistant automations from the same push notifications the 1KOMMA5° mobile app receives. Payload is a flat dict with plain JSON types:

- `system_id` (string) — the 1KOMMA5° system UUID
- `notification_id` (string) — unique per notification
- `type` (string) — e.g. `ENERGY_MARKET_UPPER_TARGET_REACHED`, `ENERGY_MARKET_LOWER_TARGET_REACHED`, `SYSTEM_HEALTH`
- `title` (string \| null) — already localized to your account language
- `body` (string \| null) — already localized
- `locale` (string \| null) — e.g. `"de"`
- `created_at` (string \| null) — ISO-8601
- `meta` (dict) — type-specific extras, e.g. `meta.price.value` for price-threshold events

**Example automation** — surface any cloud notification as an HA persistent notification:

```yaml
alias: 1KOMMA5° notification passthrough
trigger:
  - platform: event
    event_type: onekommafive_notification
action:
  - service: persistent_notification.create
    data:
      title: "1KOMMA5°: {{ trigger.event.data.title }}"
      message: "{{ trigger.event.data.body }}"
      notification_id: "onekommafive_{{ trigger.event.data.notification_id }}"
```

Filter by `type` to only react to specific notification kinds (e.g. only fire on upper-price thresholds).

**Dedup persists across HA restarts.** State is stored under `.storage/onekommafive.notifications.<entry_id>` via HA's `Store` helper. The first refresh after a fresh install captures the current-window horizon and fires nothing — no "welcome to HA, here are your last 30 days of notifications" flood.

**Which notifications reach HA?** Whatever the 1KOMMA5° cloud API returns — which appears to honour your existing per-type subscription settings in the 1KOMMA5° app (Settings → Notifications). If you have a notification type disabled in the app, HA won't see events of that type. Nothing to configure on the HA side.

**Service `onekommafive.get_heartbeat_metrics(window)`.** On-demand fetch of aggregated 1KOMMA5° Heartbeat metrics for a chosen time window — `day` / `week` / `month` / `half_year` / `year`. Returns a flat dict with all populated `HeartbeatPriceWindow` fields (~22 per window: PV / grid kWh, tariffs, €-amounts, VAT, plus a couple of composite metrics you can choose to ignore). Absent windows respond `{"window": ..., "available": false}` so callers can branch on it. Useful for sanity-checking cloud-side aggregates against your locally-integrated Long-Term Statistics.

```yaml
alias: Cloud vs local monthly grid check
trigger:
  - platform: time
    at: "03:00:00"
action:
  - service: onekommafive.get_heartbeat_metrics
    data: {window: month}
    response_variable: cloud
  - service: notify.persistent_notification
    data:
      title: Grid import — cloud vs local
      message: >
        Cloud month: {{ cloud.grid_consumed_kwh | round(1) }} kWh /
        {{ cloud.grid_consumption_cost_eur | round(2) }} EUR.
```

**Sensor `sensor.<sys>_dynamic_pulse_price_guarantee`** (DP contract only) — raw `price_guarantee_value` from your Dynamic-Pulse subscription in `EUR/kWh`. Informational only: the guarantee comes with terms and conditions on the 1KOMMA5° side that this integration doesn't model — don't wire automations that assume "current price ≤ guarantee" semantics. Sensor is only created when a DP contract is present, so non-DP accounts stay clean.

## Added — diagnostic

**Diagnostic sensor `sensor.<sys>_diag_notification_update`** (`entity_category=diagnostic`) — timestamp of the last successful notifications-coordinator refresh, following the existing `diag_*_update` pattern.

## Changed

**`onekommafive.refresh_now` service scope** — accepts `coordinator: notifications`; `coordinator: all` refreshes it alongside the other seven.

**SDK pin raised to `>=0.1.44,<0.2`** — upstream 0.1.44 adds `get_heartbeat_prices` and `get_subscriptions`, both consumed by the two new surfaces above.

## Upgrade

Nothing required. The new event is opt-in — automations that don't listen for `onekommafive_notification` are unaffected. The DP price-guarantee sensor and heartbeat-metrics service only appear for accounts that use them. Existing entities keep their `unique_id`, `entity_id`, translation keys and long-term statistics.
