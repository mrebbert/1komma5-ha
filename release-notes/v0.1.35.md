## What's New

### Per-consumer cost sensors

Four new monetary sensors break the existing `electricity_cost` down by appliance:

| Entity | translation_key |
|--------|-----------------|
| Stromkosten Wärmepumpe | `heat_pump_cost` |
| Stromkosten Wallbox | `ev_charger_cost` |
| Stromkosten Haushalt | `household_cost` |
| Stromkosten Klimaanlage | `ac_cost` |

All use proportional allocation of the grid-import cost:

```
share = consumer_power / consumption_power
cost  = grid_consumption_power × share × stable_price × dt
```

The four values sum to the existing `electricity_cost` sensor at every sample (invariant verified by a Tier-2 test). When PV/battery cover all consumption, the grid bill is zero and all four sensors stop accumulating together.

**Note**: the 1KOMMA5° API mocks `acs_power` even for systems without an AC unit. The Klimaanlage-Cost sensor may therefore show a small non-zero value in such setups — same quirk as the existing `acs_energy` sensor.

### Weather forecast

The integration now uses the `system.get_weather()` endpoint that's been available in the SDK since 0.1.16 but was previously unused.

- New `weather.<system>` entity — appears in the standard HA weather card, supports the `weather.get_forecasts` service (hourly resolution, ~48 h horizon in 3-hour buckets).
- Two extra sensors `Sonnenscheindauer heute` / `Sonnenscheindauer morgen` (minutes) — handy for PV-relevant automations ("only run the dishwasher if today gets >300 min of sun"), since the WeatherEntity schema can't carry sunshine duration directly.
- A new 1-hour weather coordinator backs both. Failures are non-fatal and retried on the next interval.

The forecast is location-correct out-of-the-box — the 1KOMMA5° cloud already knows where your system is installed. No API key, no separate weather integration needed.

### Three automation blueprints

User-importable blueprints in `blueprints/automation/onekommafive/`:

- **`cheapest_window.yaml`** — schedule a switch / `input_boolean` for the cheapest contiguous N-minute window each day. Wraps the `onekommafive.get_cheapest_window` service, waits until the returned start time, then toggles the entity for the configured duration. Typical use: dishwasher, washing machine, EV manual run.
- **`follow_cheap_electricity.yaml`** — mirror a switch to `binary_sensor.…_cheap_electricity`. Opportunistic on/off for loads that are happy to run whenever power is cheap (hot-water booster, pool pump). Optional earliest/latest hour-of-day window so the load doesn't kick on at 03:00.
- **`notify_grid_charge.yaml`** — fire a notification whenever the Heartbeat AI flips `binary_sensor.…_optimization_battery_grid_charge` to ON. Templatable title and message.

Import directly from the GitHub URL via HA's blueprint importer. See [`blueprints/automation/onekommafive/README.md`](https://github.com/mrebbert/1komma5-ha/blob/v0.1.35/blueprints/automation/onekommafive/README.md) for details.

### Dashboard

The cost view now has a second `statistics-graph` below the existing cost/feed-in chart that breaks `Stromkosten` into its four per-consumer slices (heat pump / wallbox / household / AC). It reuses the same day/week/month/year `input_select` switcher — no new helper needed.

## Tooling

- **Tier-2 integration tests** added under `tests/integration/` using `pytest-homeassistant-custom-component`. Covers config flow, reauth/reconfigure, coordinators, services, options flow, cost sensor, stable price sensor, charging-mode select, weather entity, optimization bus events. Installed via the new `[test-integration]` extras group in `pyproject.toml`. New `integration-tests` CI job runs on every push/PR.
- 93 tests total (54 Tier-1 helpers + 34 Tier-2 HA-stack + 5 translation parity), ~0.9 s.
- CodeQL action bumped from v3 → v4 (Dependabot PR).
